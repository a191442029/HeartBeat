# ESP32 全屋心率中继 · 设计决策记录

> 本文档是 2026-09-24 一轮完整方案讨论的沉淀，作为实施依据。
> 目标：解决三室两厅中 PC 蓝牙覆盖不到的房间，手环心率收不到的问题。

---

## 1. 背景与痛点

- EXE 直连手环依赖 PC 蓝牙，覆盖不完整
- 家中已有 ESP32，可每房间放一台，形成"BLE 收心率 + WiFi 回传"的中继网络

## 2. 关键实测（双 PC 实验，2026-09-24）

- PC A 连上手环后，PC B 就扫描不到手环了
- 结论：**手环被连接后停止广播（"连接即静默"）**
- 由此修正设计：空闲节点无法持续"围观"被连接的手环 → 漫游改为**探测式切换**（见 §6）

## 3. 蓝牙规范查证（联网核实）

| 结论 | 依据 |
|---|---|
| 广播是一对多，多台设备可同时扫描同一手环、各自测 RSSI | Bluetooth LE Primer: "advertising may be used to concurrently transfer data to multiple scanning devices in a one-to-many topology" |
| 心率数据不走广播，走连接内 Notify（0x2A37） | Heart Rate Service v1.0: "shall be notified while in a connection" |
| 0x180D 出现在广播包中只是"服务目录声明"，不含心率数值 | 广播包 31 字节限制 + HRS 规范 |
| 小米手环无"广播心率模式"（Polar H10 等才有） | ESPresense 文档佐证 |

**术语纠正**："心率广播"的说法不准确——广播里只有招牌（0x180D 服务声明），心率数值必须靠连接推送。

## 4. 总体架构

```
手环 --BLE(同房间)--> ESP32节点 --WiFi--> EXE中继hub --统一入口--> 波形/日志/报警/推送
```

- **EXE = 中枢**：唯一连接管理者。节点注册表、RSSI 汇总、仲裁决策、数据汇聚。下游业务零改动
- **ESP32 = 纯执行节点**：只做两件事——举手报告（RSSI/状态）+ 服从命令（connect/disconnect）。永不自主连接
- 回程走 WiFi 不走 BLE：路由器已证明全覆盖（摄像头 RTSP 为证），BLE 回程会把穿墙难题原样搬回 PC 侧
- 共存预算：BLE 收 1 通知/s + WiFi 发 1 JSON/s ≈ 空口占空比 0.5%，无阻塞

## 5. 时机模型（何时触发连接/扫描）

1. **空闲期（无人连接）**：手环持续广播 → 空闲节点低占空比被动扫描（37%）持续测 RSSI → 每 2s 心跳上报 → EXE 自动选最强者（平滑值最大且 > -80dBm）下连接命令
2. **连接期**：手环闭麦 → 只有持有连接的节点能测 RSSI（连接事件自带），其他节点沉默待命
3. **漫游切换（探测式）**：持有者 RSSI < -75 越级上报（不等 2s 心跳）→ 连续 3 个周期确认 → EXE 下 disconnect → 手环快速广播（20~100ms/包）→ 1s 全屋扫描窗 → 选比原持有者强 10dB 以上且 > -80dBm 的最强者 → 连接。断点约 2~2.5s，波形留空、日志标记切换事件
4. **无更优者**：探测后重新连回原持有者
5. **PC 直连优先**：PC 已连手环时，强制节点 disconnect（互斥仲裁）
6. **报警期冻结**：报警（webpush `_state["alarm"]=true`）期间禁止质量切换（保数据连续）；数据中断接管不受冻结限制
7. **两个永不**：节点永不自主连接（防抢连）；报警期间永不切换（防断流）
8. **断连恢复流水线**：
   - PC 直连断开 → 现有重试 2 次 → 仲裁移交节点
   - 节点 BLE 断开 → 自愈（1/2/4/8s 指数退避重连，上限 30s）→ 30s 无心跳无数据 → EXE 仲裁接管
   - 节点 WS 断开 → 立即视为放弃连接权（防占坑）

## 6. 消息协议 v1（JSON over WebSocket，`ws://EXE_IP:8899/relay`，Bearer token 鉴权）

| 方向 | 消息 | 字段 |
|---|---|---|
| 节点→EXE | hello | name / fw / ip |
| 节点→EXE | hb（2s） | state(idle/connecting/active) / rssi / up |
| 节点→EXE | hr | bpm / rssi / ts（节点侧节流≥5s） |
| 节点→EXE | scan | rssi（scan 命令的响应，窗口内最佳） |
| 节点→EXE | evt | evt: ble_up / ble_down / ble_fail / no_band_mac |
| EXE→节点 | cfg | mac（手环 MAC，hello 后补发） |
| EXE→节点 | connect / disconnect | 连接权命令（connect 携带 mac） |
| EXE→节点 | scan | dur（探测窗时长 ms） |
| EXE→节点 | set / apply / reboot | name / host+port+token / 维护 |

默认 token：`HRMLink-ESP32-2025`；端口 `8899`；手环 MAC 取 config.ini `[Device] last_selected_device` 的 address。

## 7. 硬件与固件

- **选型推荐**：ESP32-S3（双核、共存余量大、外设富余），优先带 IPEX 外置天线版；经典 ESP32（WROOM-32）完全可用（阶段 0 直接用它验证）；C3/C6/C5 不推荐（单核/功能无关）
- **全屋统一同一型号**（RSSI 标定一致性 + OTA 固件统一）
- **固件**：Arduino + NimBLE-Arduino 2.x + WebSockets(markus sattler)；SoftAP 首次配网（热点 `HRM-Link-XXXX`，密码 `12345678`， captive portal）；BLE 4.2 参数默认即可
- 烧录只需首台一次，后续 OTA 由 EXE 下发（阶段 2）

## 8. EXE 端改动清单

- `relay_hub.py`：独立线程 + aiohttp WS server（/relay）+ 节点注册表 + 仲裁器；心率经 `set_hr_callback()` 注入 DevCtrl.on_heart_rate_update 同一下游
- `UI/RelaySettingUI.py`：**新 tab"ESP32中继"，勾选启用才启动**（config `[esp32_relay] enabled`，默认关）
- `UI/DevCtrl.py`：注册 on_hr_value 统一入口 + PC 直连状态探测
- 报警冻结：`set_alarm_check()` 钩子读 webpush `_state["alarm"]`
- 版本 v1.1.0；`relay_hub` 复用 aiohttp（EXE 已有依赖），spec 无需改动

## 9. 阶段计划

- **阶段 0（本次交付）**：单台验证——固件 + relay_hub + tab；验收=最远房间出数
- **阶段 1**：仲裁器完整漫游（探测切换/接管/冻结）+ irregularity_detector 断点保护
- **阶段 2**：OTA 升级、节点管理打磨、出包
- **阶段 3（暂缓）**：房间级声光报警（I2S/继电器）、房间级定位推送

## 10. 烧录说明（阶段 0）

1. Arduino IDE → 开发板管理器安装 `esp32 by Espressif Systems`（≥2.0.14）
2. 库管理器安装：`NimBLE-Arduino`（h2zero，需 2.x）+ `WebSockets`（Markus Sattler）
3. 打开 `esp32/hr_relay/hr_relay.ino`，选择开发板（如 ESP32 Dev Module / 你的板子对应型号）
4. USB 数据线连接，选对端口 → 上传
5. 烧录后串口监视器 115200 查看：等热点 `HRM-Link-XXXX` 出现 → 手机连接 → 自动弹配网页（或浏览器访问 192.168.4.1）→ 填 WiFi/EXE地址(电脑局域网IP)/端口(8899)/房间名 → 保存重启
6. EXE"ESP32中继"页勾选启用 → 节点列表出现该房间 → 命令连接手环测试

## 11. 全屋布点方案（2026-09-25 定稿，依据实际户型图）

户型：三室两厅四卧（北卧 + 南侧三卧）、客餐厅贯通居中、厨房/卫生间东北角、储物间东侧、阳台连东南卧。EXE 主机位于客餐厅（1号位，户型中心）。手头 ESP32 七八台，数量充裕，采用 5 台满配。

| 节点 | 位置 | 覆盖 | 摆放 |
|---|---|---|---|
| PC（虚拟节点） | 客餐厅 1号位 | 蓝牙直连优先，参与仲裁 | EXE 主机自带蓝牙 |
| N1 | 客餐厅（插 EXE 主机） | 客厅+餐厅+走廊，兼顾储物间、卫生间(弱) | 电视柜/餐边柜顶 ≥1.5m |
| N2 | 北卧 | 北卧全屋，兼厨房远端(弱) | 衣柜顶，离金属窗栏远 |
| N3 | 西南卧 | 西南卧全屋 | 衣柜顶 |
| N4 | 中南卧 | 中南卧全屋 | 衣柜顶 |
| N5 | 东南卧 | 东南卧+阳台（推拉口直射） | 衣柜顶靠阳台门侧 |

- **双通道**：客餐厅同时有 PC 蓝牙 + N1，为最强覆盖区；人在客餐厅 PC 直连，离开后仲裁自动移交房间节点，返回时 PC 夺回（§5 时机模型天然支持）
- **定位预留**：hb/hr 的 rssi 字段即房间级定位数据源；EXE 端定位器（指数平滑 + 5dB 迟滞防门口抖动）属阶段 3，可提前实现
- **富余节点**：2~3 台作备件/OTA 测试机，或阶段 3 卫生间/厨房补盲、房间级声光报警
- **摆放通则**：柜顶离地 ≥1.5m、离金属/微波炉 ≥0.5m、塑料壳明装、USB 常供电
- **验证路径（阶段 0）**：先 N1 客餐厅出数 → N2 北卧（最远跨墙）验证 → 其余复制

烧录信息（2026-09-25 首台已完成）：arduino-cli + IDE 内置 cli（`config set network.proxy http://127.0.0.1:7897` 走 Clash）；FQBN `esp32:esp32:esp32:PartitionScheme=min_spiffs`（默认 1.2MB app 溢出）；CP2102 驱动已装，COM 口自动识别；固件 1.37MB（69%），首启进入 SoftAP 配网（`HRM-Link-XXXX` / 12345678）。
